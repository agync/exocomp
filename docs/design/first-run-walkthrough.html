exocomp · first run

From a cold install to a first apply

What the operator does, what the daemon does, and the property that holds at each step — deploy, setup, register the git source and its keys, the first Ansible play, the first OpenTofu apply.

0
Deploy

One command puts the container on the box

Rootless Podman via a Quadlet unit. The daemon is installed but not yet serving — it has no identity and no keys, so it can hold nothing.

▸ you · at the host shell
$ curl -fsSL https://get.exocomp.dev/install.sh | sh installs ~/.config/containers/systemd/exocomp.container systemctl --user daemon-reload · linger enabled
● exocomp · not started
image pulled · quadlet unit ready run `exocomp setup` to give it an identity nothing is written until you do

Recovery never depends on this installer's origin. The same script is separately versioned and doubles as the restore path — the thing that brings exocomp back can never be the thing that broke.

1
Setup · a four-step wizard

Identity, then a printed way back, before anything real

The wizard writes nothing to disk until the last step. Its second screen is the one that matters most, and it will not let you past it.

▸ you · step 1 — identity
On this machine · recommended host key wrapped into a systemd credential, unwrap secret stays off the data volume (TPM-sealed if a TPM is present)
● exocomp · generating
host age identity · 32-byte DEK every other secret derives from this one root key established

Step 2 — the recovery kit is printed, and the wizard stops here

One page: the recovery key + QR, the recipients, the salt, the derivation recipe (restic, every vault-id, the state passphrases), the targets, the dead-man ping. With it and any one backup, the whole system rebuilds on new hardware.

⬖ cannot continue until you type · I HAVE STORED THIS
▸ you · step 3 — first backup
add target nas · restic · rest:https://nas01.lan:8000/exocomp
● exocomp · proving the way back
backup ok → restore drill ok canary secret round-trips · proven

You have a proven restore before you have done any real work. Setup runs a real backup and a real restore drill — an untested backup is a rumour, so the wizard refuses to call itself done on one.

▸ you · step 4 — hand over
exocomp serve operator: Dana · ntfy topic generated
● exocomp · the daemon takes the wheel

2
Register the source · three credential planes

A git repo is the source of truth — and it needs keys, both ways

Real Ansible lives in a repo: playbooks, inventory, and vaulted vars together. exocomp registers the repo and auto-syncs it. That opens three credential planes — reaching the repo, decrypting the vault, and reaching the fleet — each held in the envelope, none in the repo.

▸ you · register + deploy key
$ exocomp source add homelab \ --url git@github.com:me/homelab.git --signed add this deploy key to the repo (read-only): ssh-ed25519 AAAAC3Nz…l9 exocomp-homelab
● exocomp · syncs, pinned
cloned homelab @ v14 · signed tag verified auto-sync on push webhook + hourly pinned to the tag a gated run advances

Plane one — the repo. exocomp mints an ed25519 deploy key (or seals one you supply); the public half is all the forge ever sees. Signed tags mean a hostile commit cannot reach the fleet through the sync door.

▸ you · vault + fleet key
$ exocomp secrets add ansible-vault/homelab (paste, or derive it from the root key) $ exocomp host onboard nas.home,pve-02
● exocomp · plane two & three
vault-id homelab registered fleet key pushed · user + sudoers created known_hosts recorded & backed up

Plane two — the vault; plane three — the fleet. The vault-id password decrypts vars in the repo without ever leaving the envelope; a per-job ssh-agent loads the fleet key from memory to reach managed hosts. Onboarding records each host's key so a restore rebuilds trust.

3
First Ansible run

Run from the synced checkout, against the real fleet

No path to point at — the source is registered. exocomp runs the playbook from its synced copy, decrypts the vault with the registered id, SSHes to the inventory hosts with the fleet key, all sandboxed and redacted, through the one queue.

▸ you
$ exocomp playbook run homelab:site.yml source homelab @ v14 · inventory hosts.ini job 1 queued for the running daemon
● exocomp · live tail
TASK [base : write resolved.conf] ok: [nas.home] · ssh via fleet key TASK [base : api token] msg: [redacted · secret] PLAY RECAP nas.home ok=12 changed=3 failed=0
running homelab:site.yml ansible · 2 hosts 00:04
done homelab:site.yml exit 0 ok=12 chg=3

The secret never reaches the log. A redactor scrubs known secret values before any event is persisted, the vault password and fleet key live only in memory / a tmpfs the job discards at exit, and success is the process exit code — never something parsed out of output.

4
First OpenTofu run · two ways in

Give exocomp your state, or your whole run

OpenTofu adoption has a low door and a high door. Take the low one first: let exocomp be your encrypted, locked state store while you keep running tofu yourself. Move to the high door — runs in the server — when you want plan-and-apply through the queue.

▸ you · mode A — state store only
$ exocomp workspace add prod-net --state-only paste into your repo, then run tofu yourself: backend "http" { address = …/prod-net username = "job" password = "<bearer>" }
● exocomp · just the state
your laptop/CI runs the plan state row: ciphertext · locked per workspace TF_ENCRYPTION passphrase never leaves the box
▸ you · mode B — runs in the server
$ exocomp workspace add prod-net \ --source homelab --dir tofu/prod-net $ exocomp workspace plan prod-net +1 ~1 -0 · saved plan 8c31 · exit 2
● exocomp · plan → apply the plan
source homelab · init → own backend + bearer $ exocomp workspace apply prod-net --plan 8c31 apply complete · serial 0 → 1 · lock released
in sync prod-net serial 1 apply · exit 0

Either way the daemon holds ciphertext it can decrypt and the backup targets hold ciphertext they cannot. Mode B additionally saves the plan as a sealed artifact and applies exactly it — never a fresh plan that may have drifted. Locking is a SQLite row, correct on any storage: no cloud, no second service, no external database.

What held at every step
One queue, no side doors. Manual, scheduled, and alert-triggered runs share one history and one set of guardrails.
Secrets never surface. Not in logs, not in job events, not in the state row, not on the printed card beyond the one root key.
A job cannot read the keys. Sandboxed execution denies each run the database, the host key, and the sockets — proven by a startup probe.
Nothing is bespoke. Plain SQLite, plain restic, plain git bundles, plain age — the printed card recovers all of it with off-the-shelf tools.
