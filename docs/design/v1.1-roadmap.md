# v1.1+ roadmap — ranked

The ordered backlog for after v1.0. It draws on the target [personas](personas.md) and on
practitioner review of how Ansible and OpenTofu combine. It is a planning artifact, not a
commitment of dates.

## Already shipped, no longer backlog

Some post-v1 items are already on `main` and are listed here only so they are not mistaken
for open work: Litestream (fast-RPO replication) with reconciled restore; the
provision→onboard→converge chain with a standing tf-inventory; the `playbook run`
passthrough flags and the `--check` config-drift schedule; the ad-hoc `exocomp command` /
`exocomp ansible` verbs; the partial-success / `--tolerate-unreachable` outcome (a run whose
only non-success is unreachable hosts settles degraded, not a paging failure); the web UI
for sources, schedules, workflows, and policies; and `TF_VAR_exocomp_workspace` for
named-workspace multi-env. Details in [threat-model.md](../security/threat-model.md) and the
operations pages.

## Real-repo fit

Two representative repos gauge where exocomp fits:

- **A homelab Ansible repo** — **strong fit.** Static inventory, check-mode-disciplined,
  tag/group-organized: targeted, on-demand, and drift ops map ~1:1. The one blocker —
  scheduled runs failing/paging when a roaming laptop is offline — is covered by the
  partial-success outcome (above); ad-hoc `command`/`ansible` cover the on-demand case.
  Local-path sources (`--path`, read-only by default or `--writable`) are first-class — no forge needed.
- **A client Terraform repo (Kubernetes/GCP/SaaS, Terraform-Cloud-backed)** — **PARTIAL
  fit, bigger lift.** exocomp genuinely operates individual directory-rooted stacks
  (Mode A→B) with governed plan/apply/drift + a real secrets/cost/governance upgrade, but:
  - **Multi-workspace** — DOWNGRADED from a gap: exocomp's *named workspaces* (one workspace
    = one named encrypted state, same config via `--dir`) give the `terraform workspace
    select` effect today; `TF_VAR_exocomp_workspace` replaces `terraform.workspace`. No TFC
    or native TF workspaces needed.
  - **Provider CLIs in the run env** (`gcloud`/`gke-gcloud-auth-plugin`/`kubectl`/`helm`) —
    treated as the **system-dependency case (ADR 0011): host-provides / container-layer /
    bring-your-own-runner**. Deferred; BYO-runner is the post-v1 seam.
  - **Positioning honesty:** exocomp's sweet spot is homelab / solo / small-team
    self-hosting — for a client *team* on Terraform Cloud it is a collaboration/RBAC/hosted-UI
    downgrade even as it is a self-hosting/governance upgrade. Not a TFC replacement.

**New/open items surfaced:** a **job-completion → notify sweep** (a degraded/failed run is
recorded but not actively paged today — reactive pages off webhooks/drift/approvals, not job
outcome); **TUI parity** for the post-v1 web surfaces (fast-follow); **BYO-runner** (post-v1).

## Already decided, sits before this list

- **Post-v1 program**: Litestream (SQLite replication), **GoAlert** (on-call /
  escalation), OpenBao (secret backend). The incident/escalation need (tiered on-call, ack
  timers, auto-pause a flapping schedule) is GoAlert's remit; it is not re-listed below.
- **Pulled into v1**: the post-run health/verification gate and four cheap folds.

## TF+Ansible operational coverage

How Terraform/OpenTofu and Ansible combine in practice — grounded in
[Red Hat's Ansible-vs-Terraform](https://www.redhat.com/en/topics/automation/ansible-vs-terraform),
[HashiCorp on provisioners](https://developer.hashicorp.com/terraform/language/resources/provisioners/syntax),
and the [cloud.terraform collection](https://github.com/ansible-collections/cloud.terraform).
The operational bases are covered, and exocomp improves on the hand-rolled combination in
five ways:

1. **Safe handoff via declared outputs, not raw state.** The standard
   `terraform_provider` inventory plugin exposes the *entire* state (every attribute +
   secrets) to whatever builds the inventory; exocomp materializes only declared
   non-sensitive outputs and the play sees no state and no bearer.
2. **No provisioners, structurally.** HashiCorp calls `remote-exec`/`local-exec` a "last
   resort"; exocomp makes the clean apply→play handoff the only path, so the remote-exec
   anti-pattern is unreachable.
3. **Durable, resumable, policy-gated plan→apply→configure in one binary** (step-ledger +
   CEL plan-policy + approval) — the typical combo needs GitHub Actions/AAP to sequence
   and has no crash-resume.
4. **Both drift planes in one control plane** — infra drift (tofu plan) *and* config drift
   (ansible `--check`) through the same guardrail/notify path.
5. **Encrypted state the play never touches** (Mode B) — the standard combo hands
   state-backend creds to the inventory reader.

The gaps are a coherent, homelab-first set that fold onto existing roadmap items and lean
on v1.0 primitives (step-ledger, the Terraform→Ansible inventory handoff, host onboarding, drift plumbing, the
secret plane). Recommended near-term cut, highest homelab leverage first:

| # | Gap (combined TF+Ansible scenario it unblocks) | Maps to | Homelab | Build | Status |
|---|---|---|---|---|---|
| A | **Provision → auto-onboard → configure** as one durable chain: `tofu apply` → auto-run the onboarding runbook against the new host (fleet key, known_hosts, wait-for-SSH) → materialize inventory → play, one resumable ledger workflow | R7 (+handoff+onboard) | high | medium | **Landed** — [provision-converge.md](../operations/provision-converge.md) |
| B | **Standing handoff inventory** a workspace persists as a named inventory that scheduled/reactive plays consume, so a new VM auto-joins the recurring converge | R9 (single-ws slice) | high | medium | **Landed** — the `tf:<workspace>` standing inventory, [provision-converge.md](../operations/provision-converge.md) |
| C | **Config-drift parity**: surface the `--check` drift fold through the same drift→event→notify/gate path as tofu drift, and a combined "infra vs config drifted" view | R2 | high (config drift dominates a homelab) | small–med | **Landed** — `AnsibleDrift` sweeps beside `TofuDrift`, [playbook-run.md](../operations/playbook-run.md) |
| D | **Sensitive TF output → sealed → auto-bound** as run-secret env into the dependent configure play (closes the loop the sealing fold opened; the managed-DB-seeding case) | R3-adjacent | medium | small–med | **Landed** — the `tf:<workspace>` run-secret binding on every apply path, daemon included, [sealed-tofu-outputs.md](../operations/sealed-tofu-outputs.md) |

A/B pair naturally — together they turn "I made a VM" into "it's onboarded, configured,
and stays converged," which is the whole reason a homelabber runs IaC. Enterprise-leaning
patterns deferred: multi-workspace dev→staging→prod promotion pipelines, ITSM/change-ticket
orchestration, fleet-scale rolling reconfigure (homelab fleets are small).

Proposed follow-on: **[bootstrap-first.md](bootstrap-first.md)** — the mirror of A/D for the
Kubernetes persona (ansible bootstraps kubeadm → tofu manages the cluster): an ansible-first
chain plus an ansible-output→seal hook, built on the same order-agnostic Sequencer.

## The ranked backlog

Ordered by breadth (personas raising it) × leverage (how many scenarios it unlocks) ×
adjacency (how much it reuses primitives exocomp already has). Each item names its
persona evidence and the primitives it builds on.

### R1 — Generic governed CLI run type  *(builds on: queue, sandbox, run-secret, approval)*
A run kind for an allow-listed CLI (`wrangler`, `flyctl`, `doctl`, `gh`, `kubectl`, `helm`)
executed inside the sandbox, its provider token injected as a named run-secret, success
judged by exit code, output redacted, serialized on a concurrency key with the tofu/ansible
runs for the same app. Without it these escape governance through ansible `shell` wrappers.
The core ships — executor kind `cli`, the store-backed allow-list (`exocomp cli-tool`), a
default-deny sandbox profile with per-registration egress, `exocomp run-cli`, and the
daemon's kind router ([operations/cli-run.md](../operations/cli-run.md)). The remaining
open work is the health-gate composition (shared with the v1 probe step) and the web/MCP
surfaces for the kind.
*Evidence:* the sharpest gap for the hybrid and cloud-dev estates.
*Leverage:* every non-ansible/non-tofu deploy in a hybrid/cloud estate.

### R2 — Non-tofu drift + time/deadline signals  *(builds on: sched, /metrics staleness gauges, structured drift, reactive)*
A signal layer beyond tofu-state drift: (a) **cert-expiry** checks for certificates no
other system renews — an internal CA or an appliance admin UI; exocomp does not manage
cert lifecycle, and a Tailscale tailnet cert or an ACME reverse proxy renews itself, so
this is a niche signal, not a default; (b) **container
image-digest drift** (pinned tag → new upstream digest); (c) **host tamper** via AIDE /
ansible `--check` file-integrity as a *security-classed* signal; (d) an **RPO gauge**
(age of the last good backup/snapshot). exocomp has no "watch a clock" notion today.
*Evidence:* 4 personas; the emotional core of "warn me before it breaks."
*Leverage:* cert outages, image breakage, intrusion detection, backup freshness.

### R3 — Secret/credential rotation lifecycle  *(builds on: secrets envelope, run-secret, step-ledger, approval)*
A rotation workflow: mint a new scoped token via the provider API → reseal versioned
(old still valid) → **canary-verify** the new token → promote → **revoke old**, fail-closed
(never leave two dead tokens). Two variants: (a) **zero-downtime dual-valid** cutover for
app DB passwords / provider keys (both valid until every consumer migrated); (b) **fan-out
to external sinks** (GitHub Actions secrets, Fly app secrets). Overlaps OpenBao — decide
whether rotation orchestration lands before or on top of the OpenBao backend.
*Evidence:* 4 personas; the #1 security chore everyone skips.

### R4 — Rolling/batch execution strategy  *(builds on: step-ledger, health gate, queue)*
A run strategy that walks a host group **serially in a declared order**, health-gates
between hosts (reusing the v1 probe step), **halts on the first host that fails to recover**
leaving the rest untouched, and enforces a maintenance-window time-box (abort/pause at the
window end). Includes a **reboot-and-wait-for-node** primitive and k8s cordon/drain/uncordon.
*Evidence:* 3 personas (homelab + SRE patch sweeps, blue/green).
*Leverage:* every safe fleet-wide change.

### R5 — App-level / logical backup + verified restore  *(builds on: backup engine, hooks, sched, restore drills)*
A backup *type* distinct from restic-filesystem: **logical dumps** (pg_dump, sqlite
`.backup`, managed-DB branch export) with pre/post **quiesce hooks** (the v1 hook mechanism),
encrypted, retained. **Multi-destination fan-out** as first-class targets each with its own
credential + staleness gauge + partial-failure alert ("B2 stale 3 nights while others
succeed" — the silent 3-2-1 → 2-2-1 erosion). Restore drills that **assert the app returns**
(pg_restore --list, integrity_check, a business query), not just `restic check`.
*Evidence:* 4 personas; managed Postgres is the crown jewel restic can't walk.

### R6 — Control-plane self-DR  *(builds on: backup/recovery kit, secrets envelope, tofu state backend)*
`exocomp restore-self`: cold-rebuild the control plane from the printed recovery card —
restore its own SQLite (tofu-state backend rows, sealed secrets, step-ledger, schedules,
rules), the git deploy key, and known_hosts; solve the chicken-and-egg (the age key that
decrypts the backup containing the age key comes from the card / Shamir shares); gate on a
decrypt round-trip; refuse to auto-resume schedules until explicitly un-paused. Plus a
**rehearsable self-DR drill** against a throwaway target.
*Evidence:* 2 personas, rare-but-critical; "a control plane you can't recover is a single
point of failure holding every key." Strong candidate to promote if v1.1 has room.

### R7 — Recovery / reprovision workflow  *(builds on: step-ledger, host onboarding, host-key re-pin, restore)*
One resumable workflow: (re)image a node (PXE/netboot/cloud-init/Ignition) → run the
onboarding runbook → apply its tofu+ansible role → restore its app data from the right
restic snapshot → app-level health assert → re-join WireGuard/headscale + DNS. The v1
host-key re-pin fold covers the known_hosts-conflict step; this composes it into the
end-to-end rebuild.
*Evidence:* 3 personas (reflash/seizure recovery).

### R8 — Ephemeral environment lifecycle  *(builds on: reactive event→run, step-ledger, tofu)*
Environments keyed on an external id (PR number): paired create/destroy, a TTL, an
**orphan-reaper** that reconciles live provider resources against expected stacks (missed
teardown webhooks leak money), and a live registry visible/force-destroyable in the UI.
Adjacent: the **reversible cost-reaper** (snapshot → destroy idle cloud resource → one-command
rehydrate).
*Evidence:* cloud-dev #1 (multiple-daily) + hybrid cost-reaper.

### R9 — Unified multi-source inventory + presence-gated runs  *(builds on: the handoff inventory, run-secret, reactive)*
(a) A standing **merged inventory** unioning static local SSH hosts + multiple cloud dynamic
inventories (community.digitalocean, a Fly constructed inventory) with per-source group vars,
dedup by tailnet identity, and a **reachability pre-filter** so unreachable roaming machines
are silently excluded from a "converge all online" run rather than failing it. (b) A
**host-presence event source** (Tailscale device online / first successful SSH probe) driving
**opportunistic per-host runs** that fire when an intermittently-online machine appears,
debounced, skip-if-already-current.
*Evidence:* the headline hybrid estate's own top gaps; distinctive.

### R10 — Governance surface  *(builds on: signed refs, HMAC approvals, event log, host-path source)*
Team/compliance items from the SRE: **break-glass** audited emergency run (mandatory
justification, loud audit, reconcile-to-git obligation); **audit-evidence export** (per-change
bundle: signed commit + signer + sanitized plan + approver + outcome, tamper-evident);
**access-lifecycle offboard** (enumerate a principal's access, revoke fleet-wide, re-encrypt
sops recipients, rotate what they saw, coverage report) — the offboard overlaps R3.

## Cross-cutting note

R1's health gate, R4's rolling strategy, R6/R7's recovery workflows, and R8's lifecycle
are all **step-ledger choreographies** — the step ledger is the spine for most of this
roadmap, which is why it was built first. R2's signals feed the existing /metrics staleness
gauges and reactive rules. The roadmap is mostly *composition of primitives v1 already has*,
not new subsystems — the exceptions are R2's clock/deadline layer, R3's provider-API rotation,
and R8's external-resource reconciliation.
