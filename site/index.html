Homelab control plane

Your homelab,
one binary.

exocomp owns state, sequencing, keys and recovery in one static Go binary, and shells out to pinned tools for the work itself. State is a single SQLite file beside it — no Postgres, no Redis, no second service to keep alive.

01 Capabilities

Five capabilities, one queue.

The console, the TUI, the CLI, a schedule, a matched webhook and an MCP call all enqueue the same job before anything runs. Guardrails live in the queue, so no surface can route around them.

  • Ansible Configuration

    Playbooks, ad-hoc commands and inventories from your own git checkouts. A --check run reports drift per host, and only the count of would-change tasks, never a diff that might hold a secret.

    exocomp playbook run <playbook>

  • OpenTofu Provisioning

    Plan, read the diff, then apply the saved plan. State is served by an HTTP backend over SQLite, so MinIO and its conditional writes are not in the path, and state history comes from the database rather than a bucket.

    exocomp workspace plan <name>

  • Secrets Envelope

    One data key, wrapped to every age recipient you trust and split into purpose-bound subkeys. Run secrets reach the sandbox and stop there; the key printed at setup is the only copy at the top of the chain, and the database never holds it.

    exocomp secrets add <name>

  • Backups Three legs

    restic to a NAS, an S3 endpoint and an age-encrypted git repository. Any one target restores the control plane; Litestream keeps a continuous copy of the database beside them.

    exocomp backup run

  • Agents MCP over HTTP

    The write verbs of the API, exposed to an agent at POST /mcp behind a scoped token. Same queue, same sandbox, same approval gates as a person at the console — no ambient authority.

    POST /mcp
02 Interfaces

Healthy is quiet. Failure is loud.

The console is an instrument panel, not a dashboard of reassurance. State is a word and a colour, and signal colour is spent only where an operator has a decision to make. A nominal system shows quiet counts and an empty attention band.

Phone approvals are in development. The design and the preview are in the mobile guide.

03 Guarantees

Rules the code is held to.

Each of these is a merge-blocking invariant, not a preference. Where a feature needs one of them relaxed, the feature is what changes.

  1. 01

    One process, one file

    No Postgres cluster, no Redis queue, no consensus. A user service or a rootless container, and WAL-mode SQLite, with Litestream as an optional fast path.

  2. 02

    Nothing bespoke on disk

    Plain restic repositories, plain git bundles, plain age files, standard OpenTofu state. A restore needs age and restic, not exocomp.

  3. 03

    Exit codes decide

    Ansible, tofu and restic are trusted by exit status. Parsed output makes the UI legible and never overrules the verdict.

  4. 04

    Secrets stay out

    No secrets in logs, job events, flags, docs or test fixtures. Run secrets are handed to the sandbox and dropped there.

  5. 05

    One queue, no side doors

    A TUI keypress, a schedule, a webhook, an API call, an MCP call — all of it lands in the same FIFO before execution, which is what makes the guardrails enforceable.

  6. 06

    No sudo, anywhere

    Nothing here elevates. Work that needs root becomes an explicit request to the operator, not a privilege the daemon holds.

04 Command line

Built to be scripted.

One JSON envelope with a pinned schema_version, fixed ordering and no volatile fields: unchanged state returns byte-identical output. Exit codes carry the verdict for a shell, and the same codes carry it for an agent.

$ exocomp command --host 'web*' --output json -- hostname -f | jq
{
  "schema_version": 1,
  "kind": "command.result",
  "data": {
    "job_id": 42,
    "state": "succeeded",
    "exit_code": 0,
    "hosts": {
      "web01": {
        "status": "CHANGED",
        "rc": 0,
        "changed": true,
        "stdout": "web01.internal.homelab"
      },
      "web02": {
        "status": "CHANGED",
        "rc": 0,
        "changed": true,
        "stdout": "web02.internal.homelab"
      }
    }
  }
}
Exit codes
0ok
1generic failure
2changes present
3not found
4unauthenticated or forbidden
5conflict, or the lock is held
6awaiting approval
7busy — retry later

The process exit code and the JSON error.code are two views of the same taxonomy, so a shell and a model branch on the same integers.

The CLI, /api/v1 and MCP all marshal through this one envelope. Payloads are values-free by design: identifiers, states, keys and counts, never a secret or a raw log.

05 Recovery

The restore path does not need exocomp.

The recovery kit is printed once at setup and the key never reaches the database. The chain from that key to a running daemon is executable by hand, with stock tools and no registry.

  1. 01

    Printed once

    The age recovery key is printed at setup and never written to the database. exocomp recovery-kit reprints the recipe, not the key.

  2. 02

    Fetch the copy

    Pull the restic repository, or the encrypted git copy, from the NAS, the S3 bucket or wherever the offsite copy lives.

  3. 03

    Restore with stock tools

    recovery.sh decrypts the database and the fleet keys on a clean Linux host. It does not need the exocomp binary or this project's source.

  4. 04

    Start the daemon

    Point a fresh unit or container at the restored directory. It comes up with its state, keys and queue intact.

06 Install

One binary, wherever you keep it.

Install the release binary or build it from source. A user service and a rootless container run the same daemon and the same first-run wizard, which mints the keys and prints the recovery kit. Container installs (Quadlet, Compose) are in the bootstrap guide.

Shell 
# release binary, checksum, then the first-run wizard
curl -fsSLO https://github.com/agync/exocomp/releases/latest/download/exocomp
curl -fsSLO https://github.com/agync/exocomp/releases/latest/download/exocomp.sha256
sha256sum -c exocomp.sha256
install -Dm755 exocomp ~/.local/bin/exocomp
exocomp setup

# then keep it running as a user service
mkdir -p ~/.config/systemd/user
cat > ~/.config/systemd/user/exocomp.service <<'EOF'
[Unit]
Description=exocomp control plane
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=%h/.local/bin/exocomp serve --port 8643 --web-addr 127.0.0.1:8642
Restart=on-failure
RestartSec=3s

[Install]
WantedBy=default.target
EOF
systemctl --user daemon-reload
systemctl --user enable --now exocomp
# Go 1.26 or newer
git clone https://github.com/agync/exocomp
cd exocomp

make build          # -> bin/exocomp
make check          # fmt, vet, lint and the short test suite
make check-race     # the same gate with -race ./...

Linux. The release binary is amd64; the container image is a manifest list for amd64 and arm64, and a source build covers either. Quadlet needs Podman 4.4 or newer, building needs Go 1.26 or newer, and the web surface stays on loopback until you mint a token. The binary, the docs and the design system all live in one repository.

Why “exocomp”

In The Next Generation, an exocomp is a small, self-contained unit that reconfigures its tool bay for the job in front of it. The name is a nod, not an architecture diagram: one small process, and the tools you already run.
