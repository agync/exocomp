Origins: The Quality of Life

Named after the autonomous engineering units from Star Trek: The Next Generation. In the series, exocomps are self-contained devices equipped with a versatile tool bay that reconfigure themselves to solve unpredictable operational problems. Here, that philosophy translates to a sovereign control plane managing your fleet through standard, un-opinionated tools.

SYSTEM INVARIANTS

Architectural rules that never yield.

Every execution path, data model, and user interface surface is governed by immutable constraints. Breaking any of these fails review.

INVARIANT 01

One operator, single process, plain SQLite

No external database. No PostgreSQL cluster, no Redis queues, and no distributed consensus. Runs directly as a user systemd service or inside a rootless container with WAL-mode SQLite and continuous Litestream replication to S3 or SFTP.

Storage: SQLite WAL Local File
INVARIANT 02

Zero bespoke data formats

Nothing is stored in a proprietary format. Data stays in plain restic repositories, plain git bundles, plain age or SOPS envelope files, and standard OpenTofu state files. Recovery requires only standard open source tools.

Tools: restic · age · git Portable
INVARIANT 03

Exit codes decide correctness

Subprocess truth is strictly exit 0 versus non-zero. Parsed output enriches the user interface and agent queries, but exit codes strictly dictate state transitions, ledgers, and notifications.

Execution: Exit Codes Deterministic
INVARIANT 04

Secrets never leak

Secrets never appear in logs, CLI flags, job events, docs, commits, or test fixtures. Run secrets are injected via Landlock and bwrap sandboxed memory pipes or scrubbed environment variables.

Sandboxing: Landlock / bwrap Zero leakage
INVARIANT 05

The one queue is the only executor

Every execution path routes through the single FIFO job queue. Concurrency keys, execution locks, and approvals live in the queue engine rather than scattered application logic.

Queue: Serialized FIFO Lock Protected
INVARIANT 06

Zero sudo across the system

Nothing in exocomp runs root. It runs unprivileged as your host user or inside a rootless container. Work requiring elevation on target machines is delegated through explicit operator-approved flags.

Privilege: Unprivileged Host User Audited

DISASTER RECOVERY PROPERTY

Restore onto dead hardware in 5 minutes.

Disaster recovery never depends on exocomp itself, a running daemon, or an online container registry. Recovery relies entirely on standard POSIX tools.

STEP 1 The Recovery Card

Physical Age Key

At bootstrap, exocomp generates a printed recovery card containing the master age private key and storage locations.

STEP 2 Cold Storage Fetch

Fetch Encrypted Snapshot

Retrieve the encrypted Restic repository or Litestream WAL replica from your NAS, S3 bucket, or offsite storage.

STEP 3 Execute recovery.sh

Zero-Dependency Restore

Run recovery.sh on any clean Linux machine. Standard age and restic tools decrypt your database and fleet keys.

STEP 4 Instant Takeover

Restart Service or Container

Point your restored directory to a new service instance or rootless container. The daemon boots immediately with all state and secrets intact.

DEPLOYMENT FREEDOM

Host service or rootless container. Your choice.

No external PostgreSQL cluster, no Redis queues, and no background worker sidecars. exocomp is a single static Go binary. Run it natively as a user systemd service on your host or inside an unprivileged rootless container.

Loopback · Port 8080 · Plain SQLite 
mkdir -p ~/.config/systemd/user
cat << 'EOF' > ~/.config/systemd/user/exocomp.service
[Unit]
Description=exocomp homelab control plane
After=network.target

[Service]
ExecStart=%h/.local/bin/exocompd --port 8080
Restart=always
RestartSec=5s
Environment=XDG_DATA_HOME=%h/.local/share

[Install]
WantedBy=default.target
EOF
systemctl --user daemon-reload && systemctl --user enable --now exocomp
